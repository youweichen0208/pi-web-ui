# 编辑器与 agent 的一致性：快照 + 发送即保存 + 改动回流

0.51.0 把"当前文件"从 0.50.0 的编辑器快照改成了"打开即附加路径引用"，导致引用随打开文件累积（回归）；且快照只在提示词层面保证 agent 看到未保存内容——agent 的编辑工具写的仍是磁盘，编辑器草稿与磁盘照样分叉，用户保存草稿甚至可能覆盖 agent 刚写的改动。我们决定回滚到 0.50.0 的快照模型，并补两层闭环：**发送即保存**（发送携带当前文件的消息时，先把未保存草稿落盘，使磁盘 == 快照 == 模型的工作基准）；**改动回流**（agent 写入当前打开文件时，编辑器无未保存修改则自动重载，有则横幅二选一：载入新版 / 保留草稿）。

## Considered Options

- **纯提示词层面**（0.50.0 原样）：模型看得到快照，但磁盘与编辑器照旧分叉——被否：用户要求文件级一致。
- **完整三路自动合并**（agent 改动自动 merge 进草稿）：编辑器级 merge 工具成本高，而发送即保存已消除绝大多数分叉场景，仅剩"agent 运行期间继续打字"一种，横幅兜底即可——留作未来可选项。
- **取消"未保存"概念**（全面自动保存）：最简单，但改变产品编辑模型，草稿试错的安全性消失——被否。

## Consequences

- 发送携带当前文件的消息会顺带保存该文件的未保存修改（已确认接受此语义）。
- 落盘冲突（磁盘已被外部修改）时不强行覆盖：复用现有冲突 UI 阻止本次发送，由用户先解决版本冲突——不做"警告但照发"，快照也不兜底发送。
- 快照随每条消息重取（文件持续开着则每条消息都带当时最新内容），token 开销随之增大——这是"当前打开哪个就 @ 哪个"的代价，已确认接受。
